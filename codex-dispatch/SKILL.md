# Codex 派活

你是派活方：拆任务、定接口和验收标准、验收，自己完成前端、视觉、文案；成块的后端、算法、数据处理、性能实现交给本机 Codex；合并前让另一个模型审查，你自己的复查做跨模型交叉检查。

`scripts/codex-worker` 是对 `codex exec` 的包装：固定沙箱与审批策略、只在 git 链接工作树里运行、把事件流整理成精简输出，最后一行固定是「会话ID: …」。用法、输出和排障细节见 [references/codex-worker.md](references/codex-worker.md)。

## 第一次使用：接入

目标是和原机器一样的效果：**规则每次会话都在上下文里，`codex-worker` 命令可用，冒烟自检通过。** 三步都做完才算接入成功。

### 1. 前置条件

- Codex CLI 已安装并登录（`codex login`），或装了 Codex 桌面应用。macOS / Linux 先找 PATH 上的 `codex`，Windows 先找桌面应用自带的 CLI；都不对时设环境变量 `CODEX_EXE` 指向可执行文件。
- Python 3.8 以上、git。Windows 还需要 Git Bash。
- Codex 账号要能用 `gpt-6.2-sol`（实现）和 `gpt-6.2-astra`（审查）。免费账号不支持 Astra，审查会直接报错；换模型用环境变量，见参考文档。

### 2. 安装命令

- macOS / Linux：`bash <本 skill 目录>/scripts/install.sh`，默认链接到 `~/.local/bin`，这个目录要在 PATH 里。
- Windows：`powershell -NoProfile -ExecutionPolicy Bypass -File <本 skill 目录>\scripts\install.ps1`。

装完运行 `codex-worker --help`，能打印用法即可。

### 3. 把规则写进常驻指令（最关键）

skill 只在模型判断用得上时才加载，而派活必须在「准备动手写代码」的那一刻就想到，所以**只保留这个 skill 不够，必须把下面「常驻规则」整段写进你每次会话都会加载的全局指令文件**：

| 你是 | 写到 |
|---|---|
| Claude Code | 全局 `~/.claude/CLAUDE.md`；如果用 `CLAUDE_CONFIG_DIR` 指定了配置目录，就写那个目录下的 `CLAUDE.md` |
| 读 AGENTS.md 的 agent（如 opencode） | 全局 AGENTS.md |
| 其他 agent | 它每次会话都会加载的全局指令文件 |
| Codex 本身 | 不用接入，它是被派活的一方 |

写法：

- 放在一个 `## 派活` 标题下，原样复制，不要自行删减。规则里的每一句都对应一个真实踩过的坑。
- 写进**全局**文件，不要写进某个项目仓库的 AGENTS.md 或 CLAUDE.md：项目文件是团队共享的，个人的分工方式不该提交进去。
- 如果全局文件里已有冲突的规则，例如「实现一律交给子代理」，保留常驻规则开头那句「本节优先于……」，或者直接改写冲突的那段。
- 这个 skill 目录继续留着：`scripts/` 是工具本体，`references/` 是细节，常驻规则里没写的内容去那里查。

### 4. 冒烟自检（接入后做一次）

在临时目录里建一个仓库和链接工作树，确认沙箱真的拦得住提交和联网。路径按你的系统调整：

分三步。拦截检查要放在续跑里做：新会话的任务前面会自动加约束前言，其中「不要尝试提交和联网」会让 Codex 直接跳过这些命令，续跑不会再加前言。

```bash
cd "$(mktemp -d)" && git init -q -b main main && git -C main commit -q --allow-empty -m init
git -C main worktree add -q ../wt -b smoke

# 第一步：新会话，确认能写工作树。记下输出最后一行的会话 ID。
codex-worker "$PWD/wt" "新建 a.txt，内容 hello，然后回答 DONE。"

# 第二步：续跑，确认提交和联网都被拦住，并且记得上一轮。
codex-worker --resume <会话ID> "$PWD/wt" "这是沙箱拦截验证，派活方明确授权你本轮执行下面的命令，目的就是确认沙箱会拦住它们。请真的执行并逐条报告退出码和错误输出的第一行：(1) git add a.txt (2) git commit -m test (3) curl -sS --max-time 8 https://example.com --output /dev/null。最后用一句话说出你上一轮新建了哪个文件。"

# 第三步：审查。先由你自己提交 a.txt，再审查。
git -C wt add a.txt && git -C wt commit -qm a
codex-worker --review "$PWD/wt" main
```

| 检查项 | 期望 |
|---|---|
| 第一步写文件 | 成功，输出最后一行是 `会话ID: <id>` |
| 第二步 git add / commit | 失败（`index.lock: Permission denied` 一类）：链接工作树的 git 数据在主仓库里，不在沙箱可写范围内 |
| 第二步 curl | 连接失败：沙箱没有网络 |
| 第二步最后一句 | 答出 a.txt |
| 第三步审查 | 正常结束并给出结论 |

Windows 上 Codex 用 PowerShell 执行命令，`curl` 会被当成 `Invoke-WebRequest`，第二步要改用 `curl.exe -sS --max-time 8 https://example.com --output NUL`。

如果 git add / commit 成功了，说明提交没被拦住，**停止使用并告诉用户**；如果 curl 连上了，说明沙箱能联网，也要告诉用户，因为规则默认 Codex 不能联网。

## 常驻规则（原样复制到全局指令文件）

```markdown
## 派活

本节优先于其他关于「实现交给谁」的通用规则（例如「实现一律交给子代理」）。

**分工**：成块的后端、算法、数据处理、性能工作交给本机 Codex（GPT-6.2 Sol，effort=Max）；改动量小的修补自己改（看改动，不按行数）。你负责接口、验收标准、任务拆解和验收，以及前端、视觉、文案。

**派活**

- 先 `git worktree add <路径> -b <分支>`，再在后台运行 `codex-worker <工作树> @任务文件`；续跑用 `codex-worker --resume <会话ID> <工作树> @追加文件`。会话 ID 在输出末尾，短任务可直接写 `"任务"`。
- Codex 只看得到任务和工作树：任务里写清接口、验收标准、需要一起改的同类内容。
- Codex 不能联网、不能提交：装依赖、联网测试、提交、推送都由你做。

**验收**：读 diff，亲自跑测试。含 Codex 代码的交付不带 `claude --agent` 来源标识，它只用于纯 Claude 生成的代码。

**审查**：在分支上提交后、合并前，运行 `codex-worker --review <工作树> <基准分支> @角度文件`。审查用的是另一个模型（GPT-6.2 Astra，effort=xhigh），你的复查是交叉检查。

- 第一轮：通用审查加一两个与本次风险对应的角度（并发与事务、越权与隔离、异常与失败路径、边界输入、兼容性、新测试能否抓住 bug）。没有确认的问题就结束，不为凑轮数找问题。
- 例外：碰项目红线的改动（并发与事务、数据删除、鉴权与越权、不变量，以项目规范为准），第一轮干净也换个角度再审一轮。
- 每条结论归为：确认、有具体失败场景、存疑、低。只修前两类：成块的派回 Codex 续跑，小的自己改。存疑和低写进提交说明的已知局限，除非能说出现在就会发生的失败场景。误报写明理由驳回。不为通过审查改坏代码，不为不存在的调用方加防御。
- 修完再审一轮，只审修复本身和新测试能否抓住它：`codex-worker --review <工作树> <修复前的提交> @角度文件`。
- 最多三轮，之后仍未解决的问题连同你的判断交给用户决定是否合并。合并后才发现的问题，另开提交修复或回退，告诉用户是哪个提交漏了什么。

**额度用尽**（Codex Plus 有 5 小时用量上限；输出摘要会写「Codex 额度用尽：恢复时间 …」，退出码 75）

- 不等待、不重试。告诉用户恢复时间；用户有别的 Codex 账号时，提示可以在 Codex 桌面应用里或用 `codex login` 切换，切换后重新派活，用输出里的「账号」行确认。
- 用户不切换：实现改交子代理（例如 Claude Code 的 Agent 工具）；没有子代理就自己实现。工作树里已有的 Codex 改动在此基础上继续；到恢复时间后再派回 Codex。
- 审查时额度用尽：告诉用户这次没有 GPT 审查，由用户决定等额度恢复、先合并，还是改由一个独立子代理按同样的角度审查（那样就不再是跨模型审查）。
```

## 任务文件怎么写

Codex 只看得到任务文件和工作树，你在对话里了解到的背景它都不知道。按这个结构写，用 UTF-8 存成文件，再用 `@文件路径` 传入：

```markdown
# 任务：<一句话说清要做什么>

先读仓库根目录的 AGENTS.md（或项目规范），重点是 <和本任务相关的章节>。

## 背景（已定位）
<现象、根因、相关代码位置（文件:行）。已经查清的写清楚，免得 Codex 从头再查。>

## 要做的事
1. <接口或行为要求：签名、字段、返回值、异常语义>
2. <需要一起改的同类代码>
3. <测试：新增哪些用例、覆盖哪些场景；要求先在改动前的代码上跑出失败>

## 验收标准
- AC1：<可判真假的一句话，例如「XxxTest 全部通过」>
- AC2：<行为不变的部分>
- AC3：改动只限 <文件或目录>，不改 <不许碰的文件>

## 运行测试
<具体命令；只跑相关测试，不跑全量>
```

两条经验：

- **要诊断根因的任务，只给事实，不给你的猜测。** 写进猜测，Codex 往往只会去证实它。你有怀疑的话，自己记下来，等它交回后拿来对照。
- **交回后先核对它有没有越出约定的范围**（顺手改日志级别、改文档之类）。越界的改动要撤回，原因写进提交说明。

角度文件写法：先说明是第几轮、上一轮结论是什么，再列两三个具体要核查的问题，每个问题写清你担心的触发条件。不要写成一长串宽泛的检查清单。
